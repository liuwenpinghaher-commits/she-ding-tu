## 0. 一句话定位:这是什么系统

scribe3 是一台 **"按视角投影知识帧 → 只把帧喂生成 → 事后兜底校验" 的限知长篇小说引擎**。

它存在的全部理由,是支撑一个核心动作:

```
project_frame(focalizer, chapter) ——
  「在第 N 章,以某角色为视角,他到此刻为止知道哪些事实」
```

整个数据模型都是为这个动作服务的。理解这一点,就能理解为什么本系统不是"把设定塞进一个大 JSON",而是把世界拆成 **持续体 / 发生体 / 命题 / 知识边** 四类一等公民,并给每条状态都钉上"故事时间轴(章号)"。

判断任何一个字段是否"业务合理",只要过三连(承接业务审计 §0):
1. 它服务于"投影出某 knower 在某 chapter 的知识帧"吗?(**限知**)
2. 它带"故事时间轴(章号)"吗?系统所有读路径都是 `_at(chapter)`;无章号锚的状态字段几乎都可疑。
3. 私密内容若明文存在某字段、又走任何全读路径,它就是**错模**。

## 1. 本体哲学:四类一等公民与 BFO/DOLCE 红线

scribe3 的本体不是凭空设计,而是对齐上层本体论(BFO/DOLCE)的"持续体 vs 发生体"区分。这条红线决定了整张 schema 的形状。

### 1.1 持续体(continuant) vs 发生体(occurrent)

| | 持续体 Continuant | 发生体 Occurrent |
|---|---|---|
| 本系统对象 | `Entity`(角色/地点/物件/阵营) | `Event` |
| 时间部分 | **无**——它在每个时刻"整个地"存在;跨章是同一身份 | **有**——它占据故事的一段时刻,本身就是"发生" |
| 例子 | 焦三(role:焦三)从头到尾是同一个焦三 | "焦三在第 3 章炼成镇煞钉"是一次发生 |
| 怎么变 | 状态变化**不**直接改持续体,而是写一条新 `Fact`(quality@章) | 事件用 `effects` 初始化新 `Fact`,从而改世界状态 |

**为什么重要**:如果把"焦三的能力"直接当成 `character.ability` 字段去改,你就丢掉了时间——第 3 章前他没这能力、第 3 章后才有,这个"何时获得"无处安放。本系统的做法是:能力是一条 `Fact(entity=role:焦三, attribute=能力, value=御铜, valid_from=3)`,它在 `[3, ∞)` 期间"随时间索引地 inhere(内在于)"焦三。这就是 quality 模型。

### 1.2 命题即 quality(状态@章)

`Fact`(DB 表 `proposition`)不是"知识",而是 **"某 Entity 的某 attribute 在 `[valid_from, valid_to)` 期间取某 value"** 的客观状态。它是 **fabula(故事底层事实)的唯一真相源**。

> 命名提示:dataclass 叫 `Fact`,DB 表叫 `proposition`,概念叫"命题/quality"——三者同一对象。

### 1.3 知识非闭包(no logical closure)

`KnowledgeEdge`(DB 表 `knows`)是 **"某 knower 对某 Fact 的视角(belief base)"**,显式、可错、**非闭包**:

- **显式**:角色知道一个事实,必须有一条边。没有边 = 不知道(无知是默认)。
- **可错**:`polarity=False` 表示"误信/假情报"(切片暂未用)。
- **非闭包**:角色知道 A、且 A 蕴含 B,系统**不**自动让他知道 B。推论必须独立发一条 `acquired_via=inferred` 的边。

这是限知范式的命门:**限知门控的唯一来源是 KnowledgeEdge,不是 `secret` 标志**。`secret` 只是 `verify` 阶段的元数据(用来扫穿帮破绽词),它**不**做投影门控——投影门控只看"有没有 KnowledgeEdge"。

### 1.4 单一写入口("渲染只读")

改世界状态的唯一入口是 `SurrealStore._execute_write`(store.py:193)。所有 `add_*` / `supersede_*` / `RELATE` 都经此单点。这对应"渲染只读"原则:生成/渲染阶段不准改世界,只能读投影出来的帧。

## 2. 数据模型全景:运行态 26 张表分五簇(迁移定义 28 张)

> **表数口径(已更新)**:迁移 `DEFINE TABLE` 共 **28 张**;`word_stats`(034)与 `voice_sample`(039)已 `REMOVE TABLE`,**运行态实际 26 张**。本会话作者工具新增 **`volume`(卷)**(044)与 **`daily_progress`(每日码字账)**(043)两张表——见簇四、簇六。

下面把全部表按职能分五簇。每簇说明:**它建模什么 → 关键字段 → 为何这样设计**。

> 表名后标注:`SCHEMAFULL`=强约束防 LLM 写脏;`SCHEMALESS`=可变元数据;`RELATION`=图边(SurrealDB 的 `RELATE a->edge->b`)。

### 簇一 · 实体层(设定圣经的"名词")

7 张表:`character` / `place` / `faction` / `item` / `term` / `world_rule`(+ 概念上的实体扩展)。

| 表 | 建模什么 | 关键字段 |
|---|---|---|
| `character` (SCHEMAFULL) | 角色持续体 | `name`(非空) `aliases[]` `backstory`(冰山私密前史) `backstory_secret`(私密标志) `personality_tags[]` `importance` `surface_goal/deep_need/internal_conflict/fear`(角色弧光四维) `appearance/personality_detail/abilities/weaknesses` `first_appearance`(首登场章,CodexView 排序消费) |
| `place` (SCHEMAFULL) | 地点持续体 | `name`——**注意**:027 曾扩 geography/notable_events 等四字段,均无写读 UI,038 已删,`place` 现退化为纯名字表 |
| `faction` (SCHEMAFULL) | 阵营/组织 | `name`(UNIQUE) `ideology` `leader` `public_face`(明面) `private_operation`(暗线) `private_operation_secret`(私密标志) `status`(active/dissolved/dormant/reformed) `known_members[]` `first_mention_chapter` |
| `item` (SCHEMAFULL) | 物件/道具(契诃夫之枪) | `name`(UNIQUE) `category` `description` `current_owner` `symbolic_state`(active/lost/destroyed/unknown) `state_history[]`(状态变迁台账) `special_properties[]` `first_chapter` |
| `term` (SCHEMAFULL) | 专名/术语 | `name`(UNIQUE) `category` `definition` `aliases[]` `first_mention_chapter` |
| `world_rule` (SCHEMAFULL) | 世界规则(硬魔法体系) | `name`(UNIQUE) `category` `source`(力量来源) `capabilities[]`(能力) `cost`(代价) `limitations[]`(限制) `exceptions[]`(例外) `scope` `established_chapter` `note` |

**这一簇为什么这样设计**:这是"设定圣经的名词部分"——世界里有哪些人、哪些地方、哪些组织、哪些物件、哪些术语、哪些规则。`world_rule` 的字段直接对标 Sanderson 硬魔法的"能力/代价/限制/例外"四维(见 §6)。`item.state_history` + `symbolic_state` 是"契诃夫之枪"的状态台账。

**本体逃逸(已知建模债)**:本体宣称"四类一等公民",但**只有 character/place 真走 Entity 抽象**;faction/item/term/world_rule 在 store 层另起独立表 + 独立 CRUD,name 加了 UNIQUE 但不纳入统一 Entity。这是"本体 vs 持久层"的断层(详见 §9 改进 G)。

### 簇二 · 命题知识(限知核心,系统心脏)

3 张表:`proposition`(命题/事实) / `knows`(角色知识边) / `reader_knows`(读者知识边)。

```
character ──knows──> proposition <──reader_knows── (reader)
                       (= Fact, quality@章)
```

| 表 | 建模什么 | 关键字段 |
|---|---|---|
| `proposition` (SCHEMAFULL) | quality:某 entity 的 attribute 在 [valid_from,valid_to) 取 value | `entity_id` `attribute` `value` `valid_from` `valid_to`(null=惯性持续) `secret` `leak_markers[]`(破绽词) `embedding`(语义召回向量) `ingest_seq`(回写溯源) |
| `knows` (RELATION character→proposition) | 角色 belief base | `since_chapter` `until_chapter`(null=不遗忘) `polarity`(false=误信) `acquired_via`(saw/told/inferred/given/learned/narrated) `certainty`(0–1,**036 已落列**,DEFAULT 1.0) `ingest_seq` |
| `reader_knows` (SCHEMAFULL) | 读者已知(戏剧反讽的一极) | `proposition`(oid 字符串) `since_chapter` `ingest_seq` |

**为什么 reader 单独一张表而不是 `knows` 的一行**:reader 不是 character,让它走 `character→knows→proposition` 会破坏 RELATION 的类型安全(FROM character)。单独表把"读者帧"隔离,knower 隐含=reader。

**戏剧反讽是可计算查询**(knowledge.py:43):
```
dramatic_irony = KNOWS(reader, F) ∧ ¬KNOWS(focalizer, F)
```
读者已知、视角角色尚不知的事实——这是"读者揪心、角色蒙在鼓里"的张力点,系统能直接算出来,不靠人脑事后判断。

### 簇三 · 事件图(因果连贯性)

5 张表:`event` + 4 条图边 `involves` / `causes` / `causal` / `character_relation`。

```
        ┌─involves(role:SUBJ/OBJ/WITNESS)─> character
event ──┼─causes──────────────────────────> proposition  (effects:看见即知道的种子)
        └─causal(ctype)──────────────────> event         (因果链)

character ──character_relation(relation, since_chapter, until_chapter)──> character
```

| 表 | 建模什么 | 关键字段 |
|---|---|---|
| `event` (SCHEMAFULL) | 发生体 | `event_type` `story_chapter`(**故事时间**·编年发生章) `narrative_position`(**叙事位**,option<int>,046;倒叙/闪回的讲述顺序坐标,null=与 story_chapter 同序) `motivated_by_goal`(IPOCL 硬约束) `location`(record<place>) `preconditions[]` |
| `involves` (RELATION event→character) | 参与者 + 角色槽 | `role` ∈ {SUBJ, OBJ, WITNESS} |
| `causes` (RELATION event→proposition) | 事件初始化的命题(effects) | — |
| `causal` (RELATION event→event) | 因果链 | `ctype`(因果类型) |
| `character_relation` (RELATION character→character) | 人物关系网 | `relation`(26 词:ally/enemy/kin/master_disciple/lover…) `since_chapter` `until_chapter`(关系失效) `note` |

**这一簇的核心价值**:① `causal_complete`(verify.py:55)把"连贯性"从噪声大的 LLM 评审前移成**可跑的结构查询**——每事件须有 `motivated_by_goal`,非首事件须有 `causal_in`;② `involves` 的 WITNESS 槽支撑"看见即知道"——`see_event`(knowledge.py:57)给在场目击者每条 effect 发一条 `acquired_via=saw` 的知识边,不在场者不获知。

**双轴时间线(046,作者工具)**:`event` 现带两条轴——`story_chapter`(**故事时间**:事件在编年里实际发生的章)与 `narrative_position`(**叙事位**:事件在文本讲述顺序里的位置)。两者通常一致(线性叙事 `narrative_position=null` 回退 story_chapter);倒叙/闪回/插叙时分离(故事时间早、叙事位置晚)。对标 Aeon Timeline 的 Story Order vs Narrative Order,供 `GET /timeline?axis=` 双轴切换的时间线视图消费。

### 簇四 · 手稿叙事(戏剧层 + 工艺层)

8 张表:`chapter` / `chapter_version` / `volume` / `promise` / `motif` / `intent` / `craft_rule`(+ 内存 `World.list_craft_rules`)。`volume` 是本会话作者工具新增(044)。

| 表 | 建模什么 | 关键字段 |
|---|---|---|
| `chapter` (SCHEMAFULL) | 章节正文 | `seq` `title` `focalizer`(视角角色——限知护栏的输入!) `prose` `embedding`(章向量) `qc_word_count`(字数缓存)<br>**044 作者工具增列**:`synopsis`(每章梗概,大纲/卡片用,不碰 prose) `volume`(option<record<volume>>,章→卷链接,NONE=未分卷) `sort_order`(展示排序权重,独立于 seq 故事轴,拖拽重排只动它) `label`(色彩标签 ∈ draft/revise/done/idea/beat) |
| `chapter_version` (SCHEMALESS) | 命名存档点 | `seq` `prose` `label` `kind`(checkpoint/final) `qc`(体检快照) `created_at` |
| `volume` (SCHEMAFULL,**044 新增**) | **卷:一等结构对象**(一卷含多章,`chapter.volume` 反向链接) | `title`(卷名) `sort_order`(卷展示序) `intro`(卷简介,可选) `color`(卷色带,可选) `updated`。供混合 Binder 项目树/Corkboard 卡片墙的"卷→章"层级与跨卷拖拽 |
| `promise` (SCHEMAFULL) | 伏笔台账(被开启须闭合的张力) | `text` `setup_chapter`(埋下) `payoff_chapter`(回收) `status`(open/closed) `kind`(promise/red_herring)<br>**045 作者工具增字段**:`clues[]`(内嵌数组,每条 `{chapter:int, note:string}`)——草蛇灰线"中途线索/微提醒",对标 Weiland light foreshadowing;内嵌而非独立表(强属某 promise、量小、读 promise 时一次取回) |
| `motif` (SCHEMALESS) | 母题 | `name`(喂复读白名单,本应复现的专名) `theme` `echoes` `unfolding` |

| `craft_rule` (SCHEMALESS) | per-work 题材工艺规则 | `kind`(purple_regex/artifact_craft…) `pattern` `note` |

**为什么 `promise` 是台账而非布尔**:伏笔的生命周期是 `setup_chapter → (open N 章) → payoff_chapter`。`open` 着超过 N 章未回收 = 超期(体检告警,这是"契诃夫之枪未开火"的护城河)。`kind=red_herring`(障眼法)被有意排除超期判定——它本就不该回收。

**`focalizer` 是限知护栏的物理输入**:渲染前 `project_frame(focalizer, seq)` 投影知识帧,帧外的事进不了 prompt。所以 `chapter.focalizer` 不是装饰,它决定了这一章"能看见世界的哪一面"。

## 3. 本体四 dataclass 详解(配最小数据示例)

`ontology.py` 的四个 dataclass 是整个系统的内存模型。`SurrealStore` 与内存 `World` **鸭子兼容**——`project_frame` / `dramatic_irony` 不改一行就能跑在真库上(证明限知范式在持久层照样成立)。

### 3.1 Entity(持续体)

```python
@dataclass
class Entity:
    id: str                     # 本体 oid,如 "role:焦三" / "place:乱岗"
    kind: str                   # character / place / item / faction
    name: str
    traits: dict                # backstory / aliases / personality_tags / ...
```

**oid 映射**(store.py:21):本体 id 前缀 ↔ SurrealDB 表名。`role:焦三 ↔ character:焦三`,`fact:治眼 ↔ proposition:治眼`,`ev:x ↔ event:x`,`place:x ↔ place:x`。

最小示例:
```python
Entity("role:焦三", "character", "焦三",
       traits={"backstory": "幼年丧父,母亲眼盲", "backstory_secret": True,
               "aliases": ["焦小三"], "personality_tags": ["隐忍", "孝"]})
```

### 3.2 Fact(quality · 双时态 · secret)

```python
@dataclass
class Fact:
    id: str                     # "fact:治眼"
    entity_id: str              # "role:焦三"
    attribute: str              # "心愿"
    value: str                  # "攒钱给老娘治眼"
    valid_from: int             # 故事内生效起点(章)
    valid_to: int | None        # null=惯性持续
    secret: bool                # 私密底细;泄露给非持有者视角=穿帮
    leak_markers: list[str]     # 破绽词:出现在非持有者散文里=穿帮
    caused_by_event: str | None
    tx_from: int                # 草稿版本(切片恒 0)
    tx_to: int | None
```

最小示例(一条私密命题):
```python
Fact("fact:治眼", "role:焦三", "心愿", "攒钱给老娘治眼",
     valid_from=1, valid_to=None, secret=True,
     leak_markers=["治眼", "老娘的眼睛"])
```

**`secret` 与 `leak_markers` 的分工**:`secret` 是元数据(不门控投影);`leak_markers` 是 `verify.find_leaks`(verify.py:31)的扫描词——若 focalizer 帧外这条命题的破绽词出现在散文里,就是穿帮。门控仍由"有没有 KnowledgeEdge"决定。

### 3.3 KnowledgeEdge(限知承重墙)

```python
@dataclass
class KnowledgeEdge:
    knower_id: str              # "role:焦三" / "reader" / "world"
    proposition_id: str         # = Fact.id
    polarity: bool              # False=误信
    certainty: float            # 0–1
    since_chapter: int
    until_chapter: int | None   # null=不遗忘
    acquired_via: str           # saw / told / inferred / given
```

**这是限知的承重墙**。投影规则(knowledge.py:33):
```python
known_ids = {
    k.proposition_id for k in edges
    if k.knower_id == knower_id and k.polarity
    and k.since_chapter <= chapter
    and (k.until_chapter is None or k.until_chapter > chapter)
}
```
注意 `knower='world'` 是特例——返回全知真相(一致性裁判用);任何具体角色只看有边的事实。

### 3.4 Event(发生体 · effects 驱动"看见即知道")

```python
@dataclass
class Event:
    id: str
    type: str
    participants: dict          # role(SUBJ/OBJ/WITNESS) -> entity_id
    location: str | None
    story_time: int             # 章
    preconditions: list[str]
    effects: list[str]          # Fact ids —— 看见即知道据此发边
    causal_in: list             # [(event_id, ctype)] 因果入边
    motivated_by_goal: str | None
    is_executed: bool
```

最小示例 + "看见即知道"链路:
```python
ev = Event("ev:炼钉", "炼器",
           participants={"SUBJ": "role:焦三", "WITNESS": "role:云阳真人"},
           location="place:丹房", story_time=3,
           effects=["fact:御铜"],            # 这次事件初始化"焦三会御铜"

           motivated_by_goal="给母治眼凑钱")
# see_event(world, ev) → 给 SUBJ 焦三 + WITNESS 云阳真人 各发一条
#   KnowledgeEdge(.., "fact:御铜", since_chapter=3, acquired_via="saw")
# 不在场的角色不获知。
```

## 4. 双时态机制:为什么"事实会失效"是限知的前提

scribe3 的双时态有两根轴:

| 轴 | 字段 | 含义 | 状态 |
|---|---|---|---|
| **valid time(故事时间)** | `proposition.valid_from/valid_to`、`knows.since/until_chapter`、`character_relation.since/until_chapter`、`event.story_chapter` | 事实/知识/关系在故事内何时生效、何时失效 | **已兑现(含右端)** |
| **transaction time(事务/草稿版本)** | `proposition.created`、(曾有)`event.draft_version/tx_at`、dataclass 的 `tx_from/tx_to` | 哪个草稿版本写入 | **基本退场**(死字段已删/保留为骨架) |

### 4.1 valid time 怎么支撑限知推演

`facts_at(chapter)`(store.py:475)是单点区间查:
```sql
SELECT ... FROM proposition
WHERE valid_from <= $ch AND (valid_to = NONE OR valid_to > $ch)
```
"在第 N 章有效的事实" = 左端已生效 ∧ 右端未失效。`project_frame` 在此基础上再过一道 `knows` 边,就得到"焦三在第 N 章知道的、且当时有效的事实"。

### 4.2 supersede:事实会失效(本会话新增)

**问题**:若 `valid_to` 永远是 null,事实只能叠加、永不撤销——伤愈/反目/死亡/身份反转都无法表达。这是两轮审计点名的"双时态右端集体死亡"。

**修复**:`supersede_fact`(store.py:307)——显式超越。新事实写入时,把同 `entity+attribute` 的所有**开区间先驱**(`valid_to=NONE` 且 `valid_from < since`)的 `valid_to` 置为新的 `since_chapter`,再写新命题:
```python
# 第 7 章焦三的"心愿"从"攒钱治眼"变成"报杀母之仇"
store.supersede_fact("role:焦三", "心愿", "报杀母之仇", since_chapter=7)
#   → 旧命题 valid_to=7,新命题 valid_from=7
#   → facts_at(6) 仍见"攒钱治眼";facts_at(7) 见"报仇"
```
同理:`forget_knowledge`(store.py:325)给 `knows.until_chapter` 写值(角色遗忘/记忆篡改);`evolve_relation` / `end_relation`(store.py:1015/1031)给 `character_relation.until_chapter` 写值(敌变友/师徒决裂)。**双时态右端三处(命题/知识/关系)现已全部有生产者**。

### 4.3 事件的 `story_chapter`(命名漂移收口)

事件曾有 `valid_from`(章)与 `story_chapter` 双写。`max_chapter()`(体检扫描范围)曾只读 `valid_from`,是一颗活雷(只写 story_chapter 的新事件被漏算)。040 迁移已删除退场列 `event.valid_from`,`max_chapter` 收口到唯一真源 `story_chapter`(store.py:892)。

## 5. 写读单点 + 迁移机制

### 5.1 `_execute_write`:唯一落库点

所有改世界状态的写都经 `SurrealStore._execute_write`(store.py:193)。这是开发标准的**不变量 1**——任何 `add_*`/`RELATE`/`UPSERT` 都不绕过它。好处:① 写路径可统一加事务/审计;② `transaction()`(store.py:197)能拦截块内写,拼成单条多语句 surql 提交(SurrealDB Python SDK 不支持跨 `query()` 调用的事务,故用占位符重写变量名 `$x → $x___i` 后 `BEGIN…COMMIT`)。

### 5.2 `apply_schema`:按文件名追踪迁移

`apply_schema`(store.py:172)扫 `migrations/*.surql`,以 **文件名 stem 为 key** 记入 `_migration` 表,已应用的跳过。全部 DDL 用 `IF NOT EXISTS`,故重复 apply 幂等。这套机制让 schema 演进可追溯(001→042),每个迁移文件头部注释说明"改什么、为什么、谁是 reader"。

### 5.3 幂等的 ingest(`ingest_seq` purge)

`ingest` 回写知识时给每条产出打 `ingest_seq=本章 seq`。重跑同章 ingest 前,`purge_ingest(seq)`(store.py:385)先删该 seq 的 proposition/knows/reader_knows/char_state,再重写。**手动种/作者直编的数据 `ingest_seq=NONE`,不受 purge 影响**——这条隔离让"重新吃书"不会误删人工设定。

> ⚠ 历史坑(已修):早期 ingest 解析失败时,`purge` 已先删旧产出再写空 delta,导致"一次解析失败=本章既有 ingest 知识被清空且不重建"。修复后解析失败返回可区分状态(`parse_failed`),不 purge、不 apply。

### 5.4 多书隔离(一书一 DB)

`SurrealStore` 默认 `NS=scribe3 / DB=main`。多书用"一书一 DB(db=<slug>)+ 注册表 db=_reg"(store.py:42)。建书 `create_work` 给新 DB 跑全套 `apply_schema`。

## 7. 对标基准:专业"世界圣经/连续性管理"写作工艺

本节是"最优"的来源——全网检索专业作家/编辑如何管理长篇的世界设定一致性。下面 7 条权威要点,每条带"工艺要点 + 出处",并标注**它对应本系统的哪个机制**(供 §8 差距分析直接承接)。

### 7.1 故事圣经(Story Bible / Series Bible)是"活文档"
- **要点**:故事圣经是为保持一致性而建的"故事正典蓄水池",系统性记录角色描述、关系、场景、世界规则、情节时间线;它**随故事演进而更新**(living document),不是写完就锁死的设定集。连续性是读者最容易记住、也最容易出戏的东西(eye color、年龄、时间线矛盾)。
- **标准模块**:角色档案 / 地点 / 世界规则 / 时间线(常配一张空白年历标注事件发生的月份季节)/ 关系 / 命名拼写。专业工具(Plottr、Campfire)提供可视化的角色弧光、设定笔记、时间线规划。
- **对应本系统**:`character`/`place`/`faction`/`item`/`term`/`world_rule`(名词)+ `chapter`/`promise`/`motif`/`intent`(叙事)。**本系统比通用工具多出的是"机器可计算"那一层**(知识边/双时态/因果图)。
- 出处:[Atmosphere Press · Creating a Story Bible](https://atmospherepress.com/creating-a-story-bible/)、[Tasha L. Harrison · Series Bible](https://www.tashalharrisonbooks.com/home/how-to-create-a-series-bible-for-your-fiction-series)、[Chanticleer · Continuity and Story Bibles](https://www.chantireviews.com/2020/03/09/continuity-and-story-bibles-by-your-worldkeeper-diane-garland-a-chanticleer-writers-toolbox-post/)、[Plottr · Series Bible Software](https://plottr.com/series-bible-software/)。

### 7.2 冰山理论:作者知全貌,读者只见水面
- **要点**:世界构建的"冰山"——读者只看到露出水面的一小角(对故事关键的细节),水面下庞大的背景(完整魔法体系、历史、政制)是作者自己掌握、"放在另一个文件里"的。Sanderson 的补充:除非你是 Tolkien,否则没时间造完整冰山,**靠"把少数细节做到位"让读者信任你其余都在**(iceberg tips)。
- **对应本系统**:`secret` + `KnowledgeEdge` 正是"水面/水下"的物理实现——水下(私密/未揭示)的事实存在于库里、影响逻辑,但**不进读者帧、不进非持有者 POV 散文**。这把"冰山"从作者的自律变成系统的物理隔离。
- 出处:[Wikipedia · Iceberg theory](https://en.wikipedia.org/wiki/Iceberg_theory)、[Campfire · Hemingway Iceberg](https://campfirewriting.com/learn/hemingway-iceberg-theory)、[Pandaqi · Tip of the Iceberg](https://pandaqi.com/tutorials/writing/creative-writing/worldbuilding/tip-of-the-iceberg/)。

### 7.3 连续性管理:丢的不是"东西",是"状态"
- **要点**:契诃夫之枪本质是**叙事负载下的连续性管理问题**。长篇里,被遗忘的往往不是物件本身,而是它的**状态**——它现在在哪、谁知道、谁认为它重要、它还好不好用、是否被看见、读者是否最近被提醒过(否则回收时显得"从仓库里翻出来"而非"水到渠成")。Scrivener 用 binder 颜色标记 setup/payoff 出现位置;通用做法是"从每个高潮逆查,列出影响高潮的物件/特征/台词,再回到前文埋设"。
- **对应本系统**:`item.symbolic_state` + `state_history`(物件状态台账)、`promise`(setup→payoff)、双时态 `valid_to`(状态失效)——本系统恰好把"丢失的是状态"这一洞见做成了一等公民。
- 出处:[Novelium · Chekhov's Gun Examples](https://novelium.com/blog/chekhovs-gun-examples)、[Literature & Latte · What is Chekhov's Gun](https://www.literatureandlatte.com/blog/what-is-chekhovs-gun-a-guide-to-chekhovs-gun-and-the-power-of-foreshadowing)、[Britannica · Chekhov's gun](https://www.britannica.com/topic/Chekhovs-gun)。

### 7.4 伏笔台账:setup–payoff 是一笔"债",要追踪到回收
- **要点**:契诃夫之枪 = setup(看似多余的元素)+ payoff(后续变重要)。因为读者默认作者不放废笔,埋下即承诺回收。修订会把 setup 散落到几个月、几十章里 → 必须有台账盯住"埋了哪些、还没收哪些"。
- **对应本系统**:`promise.{setup_chapter, payoff_chapter, status, kind}` + 超期告警(open 超 N 章)+ `red_herring` 排除超期——这正是台账。**缺口在作者视图**(§9 改进 C):数据有了,作者看不到一张"伏笔仪表盘"。
- 出处:[Scribophile · Chekhov's Gun](https://www.scribophile.com/academy/what-is-chekhovs-gun)、[David Farland · Foreshadowing](https://mystorydoctor.com/foreshadowing_in_writing/)、[Sudowrite · Chekhov's Gun & Foreshadowing](https://sudowrite.com/blog/chekhovs-gun-foreshadowing-the-secret-of-tension-you-cant-look-away-from/)。

### 7.5 硬魔法体系:能力 / 代价 / 限制必须成文(Sanderson 第一法则)
- **要点**:Sanderson 用个人 wiki 管理 Cosmere 巨系列,显式追踪主题、设定、人物、**魔法与政治如何运作**。硬魔法的核心是把"能力 / 代价 / 限制 / 例外"写清楚——读者满意度来自冲突由**已知规则的限制**解决,而非临时发明的能力。
- **对应本系统**:`world_rule.{capabilities, cost, limitations, exceptions, scope}` 一一对应。`validate_setting` 还能拿 `limitations` 反查正文是否越界(当前是弱启发,§9 改进 D 升级)。
- 出处:[Plottr · Series Bible Software(Sanderson wiki)](https://plottr.com/series-bible-software/)、[Andrea Cerasoni · Iceberg Method(Sanderson)](https://andreacerasoni.com/blog/iceberg-method)。

### 7.6 限知 POV:角色只知"亲见 / 被告知 / 可推断"的事
- **要点**:第三人称限知中,叙事**经由 POV 角色的感知、知识、情绪过滤**,读者只知道该角色知道的;一个 POV 角色只能知道他**亲见(witnessed)、被告知(told)、或可合理推断(infer)**的事,要"主动利用知识缺口"。要严防 head-hopping(一个场景只锚一个 POV)。多 POV 时按章切换,但同一场景永不并存两个角色的内心。
- **对应本系统**:这是 scribe3 的**核心卖点**,且**字面对应**——`KnowledgeEdge.acquired_via ∈ {saw, told, inferred, given}` 正是"亲见/被告知/可推断";`chapter.focalizer` 锚定单一 POV;`project_frame(focalizer, ch)` 把帧外的事物理性挡在 prompt 外(防 head-hopping/越界,不靠作者自律)。**本系统把这条"作者纪律"升级成了引擎不变量**。
- 出处:[World Anvil · 3rd Person POV Guide](https://academy.worldanvil.com/blog/3rd-person-pov-the-fantasy-writers-complete-guide)、[Bridge Publisher · Third Person Limited vs Omniscient](https://bridgepublisher.com/third-person-novel/)、[Kindlepreneur · Point of View](https://kindlepreneur.com/point-of-view/)。

### 7.7 时间线与关系网:沿时间轴可视化,且会演变
- **要点**:圣经标配时间线/年历(谁在第几章/哪个季节做了什么、并行线如何交织);关系网不是静态——盟友会反目、师徒会决裂,需要能沿剧情回放边的生灭。专业工具(Plottr/Campfire)的卖点正是把弧光、时间线、关系做成可视化。
- **对应本系统**:数据全在(`event.story_chapter`、`char_state.chapter`、`character_relation.since/until_chapter`、`supersede` 失效点),**缺的是可视化视图**(§9 改进 A/B):时间线泳道 + 关系网按章回放。
- 出处:[Plottr · Series Bible Software](https://plottr.com/series-bible-software/)、[Figments and Fables · Series Bible Guide](https://figmentsandfables.com/2022/03/29/step-by-step-guide-to-writing-a-series-bible-for-television-and-novels-part-i-of-iii/)、[K.M. Allan · Series Bible](https://kmallan.com/2019/03/22/series-bible-what-to-include-why-writers-should-have-one/)。

> **三句话总括对标结论**:① 通用世界圣经工具(Plottr/Campfire/Scrivener/wiki)做的是"作者能查阅的静态记录 + 可视化";② scribe3 在此之上多出一整层"**机器可计算的连续性**"——知识边、双时态、因果图、戏剧反讽查询、穿帮扫描;③ 但 scribe3 **倒过来欠了通用工具的强项**:作者视图/可视化(时间线、关系演变史、伏笔仪表盘)。差距与改进即围绕这"一长一短"展开。

## 8. 差距分析:数据库有能力 vs 写作工艺还缺

把 §7 的专业实践与本系统数据模型逐条对照。**结论先行**:scribe3 在"机器可计算的连续性"上**远超**通用世界圣经工具(命题知识图、双时态、限知边、戏剧反讽查询、因果完整性查询都是 Plottr/Campfire 这类工具没有的);但在"作者视图/工艺呈现"上**落后**——数据库存得下、算得出,可作者看不到、用不上。

### 8.1 建模到位(本系统的护城河)

| 工艺要求 | 本系统实现 | 优势 |
|---|---|---|
| 谁在何时知道什么(限知 POV) | `knows`/`reader_knows` + `project_frame` | **物理隔离**:帧外的事进不了 prompt,不是靠作者自律 |
| 连续性自动检测 | `facts_at` 区间查 + `find_leaks` + `causal_complete` | 把"连贯性"从人脑/LLM 评审前移成**结构查询** |
| 事实会变化(时间线) | 双时态 `valid_from/valid_to` + `supersede` | 同一属性的历史值可回溯到任意章 |
| 戏剧反讽 | `dramatic_irony` 查询 | **可计算**地找出"读者知、角色不知"的张力点 |
| 硬魔法体系(能力/代价/限制) | `world_rule` 四维字段 | 直接对标 Sanderson 第一法则的成文化 |
| 契诃夫之枪(物件状态台账) | `item.symbolic_state` + `state_history` + `validate_setting` | destroyed/lost 物件若在正文复用,自动报矛盾 |
| 伏笔台账(setup→payoff) | `promise` + 超期告警(per-work 阈值) | open 超 N 章自动告警 |

### 8.2 还缺(数据库有能力,写作工艺没兑现)

| 缺口 | 现状 | 工艺要求 |
|---|---|---|
| **时间线可视化** | `event.story_chapter` + `facts_at` 数据全在,但无"按章铺开的事件/状态时间轴"视图 | 专业圣经标配"日历/时间线"(谁在第几章做了什么、并行线如何交织) |
| **人物关系演变史** | `character_relation` 有 since/until + `evolve_relation`,但前端只画"当前关系",看不到"从盟友→反目"的演变史 | 关系网应能按章回放,展示边的生灭 |
| **伏笔台账的作者视图** | `promise.payoff_chapter` 写得进,前端不显;超期告警散落两处 | 作者需要一张"伏笔仪表盘":哪些埋了未收、还剩几章超期、哪条是 red_herring |
| **设定冲突检测的覆盖面** | `validate_setting` 只覆盖物件状态/OOC/规则关键词四类,且规则匹配是裸 `lim[:4] in prose` 的弱启发 | 应覆盖时间线矛盾、能力越界、关系矛盾、年龄/外貌漂移 |
| **char_state 快照进生成** | `char_state_at` 能算时点快照,但默认不注入续写 prompt(部分批次已接) | 写第 N 章时生成器应知道角色此刻能力/性格 |

## 9. 最详细改进方案

> 每条:**现状 → 工艺要求 → 具体改法(表/字段/端点/UI)→ 优先级**。优先级 P0(卖点级)> P1(长篇必需)> P2(闭环兑现)> P3(清债)。

### 改进 A · 时间线可视化(TimelineView) 〔P1〕
- **现状**:`event.story_chapter`、`facts_at`、`char_state.chapter`、`promise.setup/payoff_chapter` 数据齐全,但没有任何"按章横铺"的视图。作者无法一眼看出"第几章发生了什么、哪些状态在此变化、哪些伏笔在此埋下/回收"。
- **工艺要求**:世界圣经标配时间线/日历(见 §7),把事件、状态变迁、伏笔生灭、关系演变沿章号铺成泳道。
- **具体改法**:
  - 端点:新增 `GET /timeline?from=&to=` —— 聚合 `events_at` 区间、`char_state`(按 chapter)、`promise`(setup/payoff)、`character_relation`(since/until)、`supersede` 产生的命题失效点,统一成 `[{chapter, kind, label, refs}]`。
  - UI:新增 `TimelineView.jsx` —— X 轴章号,泳道:事件 / 角色弧光 / 伏笔 / 关系。点击节点跳到对应章/实体。
  - 无需改 schema(数据已在)。
- **优先级 P1**:这是把"数据库已算出的连续性"变成"作者能用的工艺视图"的最大杠杆。

### 改进 B · 人物关系演变史(关系网按章回放) 〔P1〕
- **现状**:`character_relation` 有 `since_chapter/until_chapter`,`evolve_relation`/`end_relation` 能写失效,但 `graph()`/AtlasView 只渲染 `relations_at(当前章)` 的快照,看不到"边的生灭史"。
- **工艺要求**:关系网应能按章回放,展示"第 5 章他俩是师徒、第 12 章决裂、第 20 章反目"的弧线(见 §7 关系映射)。
- **具体改法**:
  - 端点:`GET /relations/history?a=&b=` 返回某对角色的全部关系区间;`GET /graph?chapter=N` 已支持按章,补一个时间滑块驱动。
  - UI:AtlasView 加章号滑块,拖动即重渲 `relations_at(ch)`;角色详情页加"关系演变史"列表(relation × [since,until])。
  - schema 无需改(`until_chapter` 已落)。
  - 顺带修:AtlasView `REL_COLOR` 补全 26 词中文关系配色(029 OVERWRITE 后 schema 已 26 词,前端只认 5 英文词——这是关系可视化遗留缺口)。
- **优先级 P1**。

### 改进 C · 伏笔台账作者视图(PromiseDashboard) 〔P1〕
- **现状**:`promise` 表完整,但 `payoff_chapter` 前端不显示;超期判定阈值 `overdue_threshold` 已 per-work 可配(intent:main),但散落在 app.py 与前端两处实现,有漂移风险;`red_herring` 已排除超期。
- **工艺要求**:作者需要"伏笔仪表盘"——埋了哪些、收了哪些、还剩几章超期、哪条是障眼法(见 §7 契诃夫之枪/伏笔台账)。
- **具体改法**:
  - 端点:`GET /promises/ledger` 返回 `[{text, setup_chapter, payoff_chapter, status, kind, chapters_open, overdue:bool}]`,超期计算**单源**(读 `intent.overdue_threshold`,删前端重复实现)。
  - UI:`PromiseDashboard` 分三栏:已埋未收(按超期紧迫度排序,标红)/ 已回收(setup→payoff 连线)/ red_herring(单列,不计超期)。
  - 校验:`advance_promise` 时断言 `payoff_chapter >= setup_chapter`。
- **优先级 P1**。

### 改进 D · 设定冲突检测扩面(validate_setting v2) 〔P0〕
- **现状**:`validate_setting`(store.py:1358)只覆盖 ① 物件状态矛盾 ② OOC ③ 规则关键词(裸 `lim[:4] in prose` 弱启发)④ 命名一致性,且第④项只收集 `known_names` 没真比对。
- **工艺要求**:连续性编辑要防的是时间线矛盾、能力越界、关系矛盾、年龄/外貌漂移(见 §7 连续性管理)。
- **具体改法**:
  - **时间线矛盾**:正文提到的事件/状态若其 `valid_from > 当前章`(尚未发生)或 `valid_to <= 当前章`(已失效),报矛盾。利用 `facts_at` 反查。
  - **能力越界**:`world_rule.limitations` 从"关键词包含"升级为结构化断言(规则 DSL 或 LLM 判官 + 证据回链),降低误报。
  - **关系矛盾**:正文若把 `relations_at(ch)` 中已 `enemy` 的两人写成协作,报提示。
  - **POV 越界(复用 find_leaks)**:把 `find_leaks` 的帧外私密扫描纳入 `validate_setting` 统一出口。
  - 端点:`POST /validate` 已存在,扩 hints 类型;前端"诊断/一键修"消费。
- **优先级 P0**:连续性自动检测是本系统对标专业编辑的核心卖点,当前覆盖面偏窄。

### 改进 E · char_state 快照常驻注入续写 prompt 〔P1〕
- **现状**:`char_state_at` 能算时点快照(能力/关系/性格),部分批次已接入,但非默认全链路注入。
- **工艺要求**:写第 N 章时生成器应知道 focalizer 此刻的弧光状态(能力到哪、性格转到哪),否则会写出"已黑化的角色还在说圣母台词"。
- **具体改法**:在续写 prompt 构造处(gen3/scenario)对 focalizer 调 `char_state_at(focalizer, seq)`,把 `abilities/personality/arc_phases` 压成简短 block 注入,与 `_frame_block`/`_recap_block` 并列。
- **优先级 P1**。

### 改进 F · MCP 召回的限知门控收口 〔P0〕
- **现状**:REST `_facts`/`/graph` 已屏蔽 secret,但业务审计指出 MCP 召回工具(`s3_semantic_recall`/`s3_hybrid_recall`/`s3_graph_recall`/`s3_dramatic_irony`)历史上明文吐 secret value 且无 focalizer 门控。需复核当前是否已统一。
- **工艺要求**:限知是卖点,任何读出口都不该让私密原文裸奔进主编 agent 上下文。
- **具体改法**:给 semantic/hybrid recall 加 `focalizer` 参数(无则按 world 全知,但 secret 打码);把"secret 无对应 knowledge 边时默认 deny value"做成统一的读出口拦截器(消除"门控 vs 元数据"双轨)。
- **优先级 P0**(限知正确性)。

### 改进 G · 本体逃逸收口(Entity 统一 or 坦诚分立) 〔P2〕
- **现状**:character/place 走 Entity;faction/item/term/world_rule 在 store 层独立表 + 独立 CRUD,name 已加 UNIQUE 但不纳入统一抽象。
- **工艺要求**:这是建模决策,不是接线。要么把四类真正纳入 Entity(统一 resolve/召回/图谱),要么坦诚承认它们是"设定圣经独立子系统"。
- **具体改法**(二选一):
  - 路线一(统一):四类各建 `Entity(kind=...)` 视图,`resolve_entities`/`graph` 统一处理;独立表降为 Entity 的扩展属性表。
  - 路线二(分立):明确文档化"设定圣经子系统",保证 CRUD 语义正确(UNIQUE + UPSERT 已做),不再假装它们是 Entity。
- **优先级 P2**(现状能跑,是中间态债)。

### 改进 H · 展示性死表群:兑现或砍掉 〔P3〕
- **现状**:`voice_profile` 9 节中 `sentence_patterns/vocabulary_profile/internal_monologue_style` 历史上零消费(YAGNI);`craft_rule.artifact_craft/cover_action` 枚举无消费者;`motif.echoes/unfolding` 仅展示。
- **工艺要求**:声音指纹/工艺规则要么真进生成 prompt,要么从 schema 删,别留"看得见不落地"的误导。
- **具体改法**:逐字段二选一——接入生成(如把 `internal_monologue_style` 真喂内心独白锚)或迁移删除。已接活的(reference_lines/catchphrases/tone_rules 进续写)保留。
- **优先级 P3**(清债)。
