# 设定库重构文档 · Codex 2.0(故事圣经)

> 日期 2026-06-21 · 适用 scribe2(SurrealDB + Hermes 底座) · 目标:把"设定库"从一张平铺的设定百科,重构成**能产出并守护"乱世铜炉级"设定品质**的故事圣经系统。
>
> 三路调研支撑:① 9 个专业工具(World Anvil / Campfire / novelcrafter / Sudowrite / Scrivener / Plottr / yWriter / One Stop / Obsidian / Notion);② 中文网文惯例 + 西方框架(雪花法 / Sanderson 三定律 / Character Arc / MICE / SillyTavern lorebook 注入机制);③《乱世铜炉》原文设定手法分析。

---

## 0. 核心论点(TL;DR)

设定库**不该是平铺的设定百科**,而该沉淀六样东西(《乱世铜炉》验证的高级设定判据):

1. **核心意象的隐喻网**(铜炉 = 世界观+主题+人物命名+物质回声,四位一体)→ 新增一等公民实体 **意象/母题 Motif**。
2. **带"代价 + 限制 + 会出什么乱子"的规则**(内丹反噬、豢兽同生死、灵龙不辨敌我)→ 规则类实体强制三字段。
3. **以"内在矛盾"定义的人物 + 声音样本**(怯懦↔为子刚烈;妖身↔比人更仁)→ 人物卡存 `核心矛盾 / 创伤 / 价值观 / 声音样本(台词)`。
4. **分层而非非黑即白的势力**(正道里有败类也有清醒者)→ 势力卡存"内部裂痕 / 异见者"。
5. **每条设定的"埋点→解释→回收"三锚节奏**(先演后说、信息延迟揭晓)→ 每条设定带三个位置锚点。
6. **跨条目一致性**(四百年/术语/年代织成隐性网)→ 一致性键 + 校验引擎。

工程骨架(专业工具 + lorebook 提炼):

- **以"场景"为枢纽建双向关系边**(`characters_present / locations / items / threads`):一份数据**双用**——既是出场追踪源,又是 AI 注入的召回源。**这是整个系统的命脉。**
- **三档 AI 注入 + 别名召回 + Progressions 按时间点可见**(novelcrafter + SillyTavern):注入集合 = 常驻 ∪ 场景关系命中 ∪ 别名关键词命中 ∪ 手动钉住,按"当前写作位置"过滤状态变更(防剧透),token 预算封顶。
- **所有 AI 写操作产出候选,经 B3 审批闸门确认后落库**;读操作(注入/检查/查询)自动。与现有架构天然契合,且被"软一致性提示不可靠"的行业教训反向印证。
- **★ 每条设定都能与主编对话式共创**(咨询/讨论/增删改查):主编 agentic 调 MCP 读工具查、写工具改(写一律走 B3 待批),复用已实现的主编 agentic + 划词引文机制。见 §7。

## 1. 现状与差距(scribe2 当前设定层)

| 维度 | 现状 | 差距 |
|---|---|---|
| 设定实体 | `setting`(name/stype/content 泛化桶)、`character`(name/motivation/voice)、`foreshadow`、`material` | 设定无**按类型的结构化字段**(地点 vs 力量体系 vs 势力 vs 物品 vs 母题混在一个桶);人物**太薄**(无 wound/lie/arc/声音样本/核心矛盾) |
| 追踪 | `relation`(src/dst)、`char_state`(逐章)、`timeline_event` | 无**场景枢纽双向边**;`char_state` 未做"按时间点可见"的注入过滤;无戏份矩阵;伏笔只有 planted/triggered/paid,无"浅/中/深 + echo + 超期告警" |
| AI 注入 | `build_writing_context` 确定性注入全量(防漂移,但**不按相关性/场景召回**) | 无三档 context、无别名召回、无 Progressions 时间门、无 token 预算策略 |
| 一致性 | `consistency.check_chapter`(LLM 对照圣经找矛盾) | 无结构化校验(数字/年代/术语/who-knows-what);依赖 LLM 软提示(噪声坑) |
| UI | CodexView = 角色/设定/伏笔/素材 四个平铺 DataTable | 无母题/势力/力量体系/地点的专属视图;无场景枢纽视图;无关系图/时间线/一致性面板;无 AI 抽取/补全入口 |

**一句话**:当前是"能存几类设定的表",缺的是"能产出并守护设定品质的系统"。

## 2. 需要哪些设定(实体类别)

**双层结构**(几乎所有专业工具的共识):**内置高频类别 + 每类预设字段模板**(降冷启动)+ **开放自定义字段**(novelcrafter Custom Details / Plottr Custom Attributes)。

推荐实体目录(★ = 必备,☆ = 按需):

| 实体 | 说明 | 对标 |
|---|---|---|
| ★ **Character 人物** | 内核驱动 + 声音 + 弧光 + 状态 | One Stop 深 schema |
| ★ **Location 地点** | 多尺度(房间→城→国),可嵌套父地点 | World Anvil |
| ★ **Faction 势力/组织** | 含公开/隐秘议程、内部裂痕 | World Anvil Diplomacy |
| ★ **PowerSystem 力量/规则体系** | 来源/规则/**代价/限制/会出什么乱子** | Sanderson 三定律 |
| ★ **Item 物品/法宝** | 持有者/位置可变(走 Progressions) | novelcrafter object |
| ★ **Motif 意象/母题**(新一等公民) | 隐喻展开 + 绑定主题句 + 物质回声清单 | 《乱世铜炉》铜炉 |
| ★ **PlotThread 伏笔/线索** | 埋点→echo→回收 三态机 + 浅/中/深 | 契诃夫之枪 / MICE |
| ★ **Event 时间线事件** | 时地人事 + 因果边 + "读者获知什么" | Plottr / Story Grid |
| ★ **Scene 场景(枢纽)** | 所有关系边的汇聚点 | yWriter |
| ☆ Species 种族 / Religion 宗教 / Language 术语词典 / Culture / Theme | 架空中文小说按需 | World Anvil |

> **为何把"母题 Motif"提为一等公民**:《乱世铜炉》最高级的不是任何一件法宝,而是"铜炉"这套贯穿世界观/主题/命名/物质意象的隐喻系统。一个顶级设定能同时回答"世界什么样 / 这书在说什么 / 角色为何如此命名 / 这个反复画面意味着什么"。设定库若只存"铜炉=一座炉子",就丢了精华。

## 3. 设定什么内容(字段)

字段标注:**[AI]** 注入 LLM 上下文 / **[人]** 纯人类组织不进 prompt / **[元]** 系统元数据。
> **关键区分**(novelcrafter):必须分清"发给 AI 的字段"与"纯人类组织字段"。Tags 不发给 AI。

### 通用字段(每个实体)
`name` 主名[AI][元] · `aliases[]` 别名/昵称/称号(**召回关键词**,大小写开关)[AI] · `type`[元] · `summary` 一句话(**优先注入**)[AI] · `description` 详述[AI] · `ai_context` 注入档(always/detected/never)[元] · `tags[]`[人] · `image`[人] · **三锚**:`anchor_seed`(首次以现象出现的章/场)、`anchor_reveal`(完整解释处)、`anchor_payoff`(回收呼应处)[元] · `consistency_keys[]`(参与一致性校验的数字/年代/术语)[元]

### ★ Character 人物(取 One Stop 深 schema + 《乱世铜炉》判据 3)
- **身份**:role(主角/反派/配角/视角)、occupation、age、gender、affiliation→Faction、外貌、衣着
- **内核(驱动行为)**:**wound 创伤** · **fear 恐惧** · **lie 错误信念** · **fatal_flaw 致命缺陷** · **want 外在目标 / need 内在需求**(二者通常对立)· values 价值观 · secrets
- **★核心矛盾 core_contradiction**(《乱世铜炉》判据 3:立体=内在对冲,如"怯懦↔为子刚烈")
- **★声音样本 voice_samples[]**(代表性台词 + 说话习惯 + 标志性思维方式;**每次写到该角色都注入**,防 OOC)——对应 MEMORY 里"角色声音"是关键修复点
- **弧光**:arc_type(正向改变/平弧/负向)、起点态→终点态、`epiphany` 顿悟、预设结局
- **关系**:relationships[](边:对象+类型+方向)
- **状态(Progressions)**:status(alive/dead/missing)+ 随场景变化的状态变更条目

### ★ PowerSystem 力量/规则体系(取 Sanderson + 《乱世铜炉》判据 2)
`source 来源` · `rules 机制` · **`cost 代价`**(硬系统核心)· **`limitations 限制`** · **`trouble_it_causes 会出什么乱子`**(《乱世铜炉》判据 2:推不出"会出什么乱子"的规则就不够好;灵龙"不辨敌我"直接酿窝里斗)· 等级/境界划分 · who_can_use · acquisition(金手指:获取方式+时机,建议尽早)· societal_impact
> ⚠️ Campfire 评测教训:"魔法规则含糊时,AI 会一边自信满满一边违背 canon"。cost/limitations 必须写硬,否则一致性提示形同虚设。

### ★ Motif 意象/母题(新,取《乱世铜炉》判据 1)
`name`(如"铜炉")· `metaphor_unfolding 隐喻展开`(天地为炉/万物为铜…)· `bound_theme 绑定主题句`(弱肉强食/普世受苦)· `material_echoes[] 物质回声清单`(香炉熄火/身成火炉/取名胡炭/赶路日头如炉…)· `naming_logic 命名逻辑`(胡炭)· related_scenes[]

### ★ Faction 势力(取 World Anvil + 《乱世铜炉》判据 4)
type · `public_agenda 公开议程 / hidden_agenda 隐秘议程` · power_structure(头衔层级)· leadership · members→Character[] · **`internal_fractures 内部裂痕 / dissenters 异见者`**(判据 4:正道里有败类也有清醒者,世界才自洽)· allies[]/enemies[](生成外交网)· territory→Location[] · identity(颜色/旗帜/符号)

### ★ Location / Item / Event / PlotThread(精简)
- **Location**:geography · climate · atmosphere(sights/sounds/smell)· history · affiliation→Faction · parent_location(层级)· `established_in`(首次确立位置,防改稿矛盾)
- **Item**:type · properties · `owner`→Character(可变,Progressions)· `location`(可变)· origin · `plot_significance`
- **Event**:in_story_date · participants→Character[] · location→ · cause/outcome · plot_thread→ · `reader_learns 读者获知什么`(管理 who-knows-what)
- **PlotThread 伏笔**:`kind`(浅<3章收 / 中 / 深结局收;或 MICE 标 M/I/C/E)· `plant 埋点`(章+原文位置)· `echoes[] 中途强化章`(深伏笔不能只埋一次)· `payoff 回收事件/章` · `state`(待埋/已埋/已强化/已回收/已废弃/**超期**)· related→Character/Item

### ★ Scene 场景(枢纽——所有关系边汇聚)
`chapter/seq` · `pov_character`→ · **`characters_present[]`→** · **`locations[]`→** · **`items[]`→** · **`plot_threads[]`→** · `status`(Outline/Draft/1st Edit/2nd Edit/Done,yWriter 五档)· word_count · goal/conflict/outcome · `offstage_characters[]`(被提及但不在场,管 who-knows-what)
> 这三/四条关系边,既是出场追踪源,又是 AI 注入召回源——**一份数据,两用**。

## 4. 怎么完成设定(创建工作流)

**自顶向下、分而治之(雪花法),分阶段写(梳理到第一卷即可,不必一次写全):**

1. **一句话**(主角想赢什么,不写人名)→ **一段**(setup + 三灾难 + 结局)
2. **世界观九维度**(地理/气候/政治/经济/社会/宗教/科技/艺术/历史)先定底层约束(地理/政体/主要冲突),再叠文化
3. **力量体系**(带 cost/limitations/会出什么乱子)
4. **人物**(want/need/lie/wound + 核心矛盾 + 声音样本)
5. **势力关系**(含内部裂痕)+ **母题**(隐喻展开 + 主题句)
6. **场景清单表**(每行一场景:pov + 出场实体 + 目标冲突)——雪花法第 8 步,公认最有用

**AI 辅助建库(降负担,草稿需确认):**
- **链式生成**(Sudowrite 范式):Braindump → Synopsis → Characters → Worldbuilding → Outline,上层喂下层,冷启动新书。
- **逐字段补全**:空字段一键生成(结合该实体其它字段 + 相关实体);不满意字段内 Rewrite。
- ⚠️ **所有 AI 产出走候选 → B3 审批闸门 → 落库**,不直接写入,避免幻觉污染设定库。

## 6. 怎么完善设定(完善 + AI)

### 6.1 AI 注入(RAG)——整个系统的命脉
复刻 **novelcrafter 三档 + SillyTavern lorebook 触发机制**:

注入集合 = `always 常驻条目` ∪ `本场景关系边命中的实体(characters_present 等)` ∪ `name/alias 关键词命中条目` ∪ `手动钉住条目`,然后:
- 按**当前写作位置过滤 Progressions**(只给已生效状态)
- **token 预算封顶**:常驻先插 → summary 优先 → 详述按相关性排序截断
- 词条字段(lorebook):`keys[]`(主触发词,支持正则)、`secondary_keys[]+logic`(AND/NOT)、`constant`(硬规则常驻)、`order`(优先级)、`recursion`(词条提别的词条→级联)、`inclusion_group`(同组命中只插一条,去重)、`sticky/cooldown`
> 注入策略三档:全量塞(仅短篇/前几章)→ 关键词 lorebook(**性价比最高的工程起点**)→ 向量 RAG + 知识图谱状态机(长篇必需)。成熟做法是 **B+C 混用**:硬规则常驻、出场实体关键词触发、剩余向量兜底。

### 6.2 AI 抽取(Extract)——从正文回填设定
从已有 prose 或外部文档抽取候选实体 + 关系,沉淀知识图谱(8 类节点 + 10 类边)。**产出走人工/B3 审批再落库**,不直接写入。

### 6.3 AI 补全 / 一致性检查 / 声音一致
- **补全**:逐字段 AI 草稿(确认后落库)
- **一致性检查(软提示,定位辅助非闸门)**:把相关设定(尤其 power 的 cost/limitations、timeline、关系状态)贴近起草上下文,标可能矛盾。⚠️ **这正是误报噪声高发区**(与 MEMORY 的 critique 噪声坑同源):魔法 cost/limitations 字段写硬 + 阈值控制 + 真正强一致性靠**结构化校验 + 审批闸门**,而非纯 LLM。
- **声音一致**:角色 `voice_samples` 每次写到该角色都注入,防 OOC。

### 6.4 活文档原则
设定随故事演进、版本化、保持精简可检索;章节↔设定双向引用;卡文时回看大纲反向校正。**贯穿铁律:AI 写操作产出候选 → 审批确认 → 落库;读操作自动。**

## 7. 设定的对话式管理(与主编探讨 / 咨询 / 增删改查)★

**定位**:设定库不只是"表单 CRUD"。每条设定都能**和主编对话式地共创**——咨询(「这个角色弧光够不够」)、讨论(「铜炉这个母题怎么深化」)、增删改查(「新建势力罗门教」「把渡叔动机改深一点」「九原渡有哪些未回收伏笔」)。这是 Codex 2.0 与"一堆静态表单"的本质区别。

### 7.1 架构:地基已具备(本项目已落地的主编 agentic + B3 审批)
主编 = Hermes `/v1/responses` + scribe2 MCP 工具(已实现并真机验证主编会调 `search_knowledge`/`list_characters` 查真实设定回答)。设定的对话式管理 = 把这套机制对准设定库:

- **读 = 咨询 / 讨论 / 查(自动,无需审批)**:`search_knowledge` / `list_entities(type)` / `get_entity` / `get_motif` / `list_scenes` / `list_open_foreshadows` / `get_author_intent`……主编实时查真实设定回答,**不凭空编**。
- **写 = 增 / 删 / 改(一律走 B3 待批写闸门)**:`upsert_entity` / `add_motif` / `add_progression` / `set_field` / `set_scene_edges` / `delete_entity`……主编**只提议草稿** → 进"待批写"队列 → 作者批准/拒绝 → 落库。**主编永不静默改设定库。**

> 这正是本文档贯穿原则"AI 写操作产出候选 → 审批 → 落库;读操作自动"的直接落地,也与现有 B3 架构 100% 契合——无需新范式,只需把工具面与 UX 补齐。

### 7.2 两个入口
1. **全局设定对话**(设定库 tab 内置一个"与主编聊设定"面板):问/改任何设定。例:
   - 查:「九原渡有哪些势力?各自的隐秘议程是什么?」→ 主编调读工具回答
   - 增:「帮我新建母题『三不渡』,展开它的隐喻并绑定主题句」→ 主编拟草稿 → 待批
   - 改:「柳娘的声音样本太少,根据已写正文补三条」→ 主编从 prose 提取 → 待批
   - 删/并:「『莲香』和『柳娘』是不是重复了?帮我核对并合并」→ 主编核对 → 提议 → 待批
2. **逐条设定讨论**(任意实体卡上「与主编讨论这个 💬」按钮):把**该实体作为上下文**带入主编对话(复用已实现的"划词→讨论"引文机制),咨询/深化/CRUD 都聚焦这一条。例:在渡叔卡上点讨论 →「他的核心矛盾写得够不够尖锐?」/「帮我把创伤补具体」。

### 7.3 主编的"设定管理"人格(区别于"写作讨论")
给主编一套设定管理指令:**先查后改**(改前必先 `get_entity` 看现状)、**改必出 diff**(原值→新值给作者比对)、**尊重一致性键**(改数字/年代/术语前先查 `consistency_keys` 有无冲突)、**写操作必经待批**(绝不假设已生效)。咨询/头脑风暴时则纯读、不写。

### 7.4 待补工程(纳入实施,见 P5)
- **MCP 工具面扩到覆盖 Codex 2.0 全 schema**:当前只有 `upsert_character`/`add_setting`/`plant_foreshadow`(粗);需补 `upsert_entity(type, fields)`/`add_motif`/`add_progression`/`set_scene_edges`/`delete_entity`/`list_entities(type)`/`get_entity`/`get_motif`,写工具一律登记进 `WRITE_GATED`(B3)。
- **UX**:设定库 tab 的全局设定对话面板 + 每个实体卡的「与主编讨论」按钮 + 待批写在设定库内可见可批(复用右轨"主编对话/待批"角标)。
- **主编设定管理指令模板**(7.3)。

## 8. 数据模型落地(SurrealDB / scribe2)

**新增/改造表**(SCHEMALESS,内容实体带 embedding+FTS):
- 改造 `setting` → 拆为按 `type` 的统一 **entity 表**(character/location/faction/power_system/item/motif/species/lore…),通用字段 + `fields`(JSON 自定义)+ `aliases[]` + `ai_context` + 三锚 + `consistency_keys[]`。或保留分表但统一字段契约。
- 新增 **scene** 表(枢纽)+ 关系边:`scene_entity`(scene ↔ entity,kind=present/location/item/thread)。**单侧录入双侧反映。**
- 改造 `foreshadow` → `plot_thread`(kind/plant/echoes/payoff/state 超期)。
- 改造 `char_state` → 通用 **progression**(entity + effective_seq + mode=add/replace + content)。
- `entity_relation` 增 `strength`(0-1)+ 方向 + 类型枚举(同盟/敌对/师徒/从属/情感/归属/位于/引发/铺垫/持有)。
- `motif` 新表(隐喻展开/主题句/物质回声)。

**注入函数**`build_writing_context` 升级:从"确定性全量"→"确定性骨架(always)+ 场景关系召回 + 别名命中 + Progressions 时间门 + token 预算"。保留确定性(防漂移),增加相关性。
