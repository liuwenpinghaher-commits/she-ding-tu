## §1 · 在回路中的位置与职责

### 1.1 门槛层的本质定位

设定圣经是 Scribe 协作回路中**作品内事实的唯一真理源(Single Source of Truth)**。

回路图中,它处于纯后台位置:

```
  人(想象 + 提意见)
        │
        ▼
  AI(全程主笔:大纲→卷→章→正文)
        │
  ┌─────┴──────────────────────────────────┐
  │         门槛层(后台隐形)                │
  │  ┌──────────────────┐                  │
  │  │  门槛1 · 连贯性保障│← ConsistencyFlag │
  │  └──────────┬───────┘                  │
  │             │  RawConflictHint[]        │
  │  ┌──────────▼───────────────────────┐  │
  │  │  门槛2 · 设定圣经(本文档)         │  │
  │  │  ① 自动注入 resolveEntities      │  │
  │  │  ② 自动校验 validate             │  │
  │  │  ③ CRUD + 版本化 + 修订回流      │  │
  │  └──────────────────────────────────┘  │
  └────────────────────────────────────────┘
        │ ContextBundle(设定切片)
        ▼
  实现4 · 记忆与检索(assembleContext)
        │
        ▼
  实现2 · 写作生成(WritingAgent)
```

**核心铁律**:设定库不做摆设——**生成时自动注入 + 生成后自动校验**。二者缺一即等于没有设定库。

### 1.2 与其他层的职责边界

| 方向 | 合作模块 | 本模块提供 | 对方提供 |
|---|---|---|---|
| **→ 实现4检索** | 实现4-记忆与检索 | `resolveEntities` 返回 `SettingItemRef[]`(候选+embedding) | `assembleContext` 按 token 预算裁剪并组装 ContextBundle |
| **→ 门槛1连贯** | 门槛1-连贯性保障 | `validate(chapterId)` 产出 `RawConflictHint[]` | 门槛1将多来源 hint 去重聚合,创建 `ConsistencyFlag` |
| **← 实现2写作** | 实现2-写作生成 | `VoiceProfile.style_summary` + `tone_rules` + `ooc_signals` 填入写作 prompt | 写作 Agent 读取 ContextBundle 中的实体切片 |
| **← 工程4版本** | 工程4-版本与回流 | 设定变更事件(消息队列) | 影响分析 `ImpactAnalyzer`,返回受影响章节集 |
| **← 原料素材库** | 原料-素材库 | 提炼好的事实条目 | 未提炼的原料(Material)候选 |

**本模块不负责**:

- 向量召回排序与 token 裁剪 → 实现4
- ConsistencyFlag 的创建、去重、人工裁决工作流 → 门槛1
- 伏笔 F-T-P 状态机 → 门槛1
- 正文生成 → 实现2
- 章节正文快照与分支 → 工程4
- LLM 调用路由与成本 → 工程3

## §2 · 设计目标与百万字挑战

### 2.1 五项设计目标

**G1 · 注入有效性**:每章写作前,自动识别该章涉及的设定实体,精准注入而非全量倾倒。避免 token 浪费与无关噪声干扰写作质量。

**G2 · 校验覆盖率**:生成后自动比对关键设定字段,覆盖 00 §5 中"世界观与设定(3 子类)"、"人物塑造(4 子类)"、"事实与细节一致性(3 子类)"共 10 类错误,以及角色声音 OOC。

**G3 · 演变可追溯**:同一角色在不同章节的状态(能力/关系/性格)有明确时间线,任何章节可查询"截至该章的当前有效状态"。设定随剧情演变而演变,不是静态档案。

**G4 · 修订即生效**:人工修改任何设定后,受影响章节自动入队重标记,无需手动同步。修订本身创建版本记录,完整可回溯。

**G5 · 高精确率优先**:遵循 00 §3 原则——宁可漏报也别误报。避免作者标红疲劳,保证门槛层真正"隐形"。

### 2.2 百万字挑战

> 【设计决策】以下量级估算在"几乎不存在经验证的百万字端到端最佳实践"背景下属设计判断,须配工程6自建度量验证。

| 挑战 | 量级估算 | 应对策略 |
|---|---|---|
| **设定规模膨胀** | 主角 10–30,次角色 50–200,SettingItem 200–800,EntityRelation 100–500,CharState 300–2000 条 | 不全量注入;按本章活跃实体分级,仅注入相关子集 |
| **设定演变版本化** | 同一设定经历 5–20 次语义变化(势力立场、能力上限等) | CharState 时间线 + SettingItemRevision 版本链;按 chapter.seq 查询时点状态 |
| **注入 token 预算** | 每章上下文约 8K–16K token;设定占比应控制在 20%–35%(1.6K–5.6K) | `resolveEntities` 只返回候选 id;实现4做 token 感知裁剪 |
| **跨模块校验一致性** | validate/门槛1/原料三方可能重复标红同一冲突 | validate 只产出"原始 hint",门槛1统一去重聚合 |
| **设定圣经自身矛盾** | 数百实体的关系网可能自相矛盾(A 是 B 的师父且 B 是 A 的师父) | 录入时同步做 EntityRelation 对称/传递约束检查 |
| **修订回流校验风暴** | 修改核心设定触发 200+ 章重校验 | 工程4先算最小影响集;批次执行(≤ 20 章/批);非核心改动降级为低优先级 |
| **VoiceProfile 误报疲劳** | ooc_signals 过严导致正常对话被频繁标红 | severity=low 的信号默认静默;规则+LLM 双重确认才产出 hint;误判后软化阈值 |

#### 3.1.2 VoiceProfile · 角色声音指纹

**位置**:`Character.voice_profile(jsonb)` 嵌套字段。

**设计动机**:【设计决策 + 已核实】ConStory(arXiv 2603.05890)将"OOC(Out Of Character)"列为人物塑造类一致性错误的第一子类【已核实】。VoiceProfile 是防止角色 OOC 的核心工具:
- 向**门槛1**提供 `ooc_signals` 规则列表,支撑自动 OOC 检测
- 向**实现2写作生成**提供 `style_summary` + `tone_rules` + `catchphrases`,直接填入写作 prompt 的"角色声音约束"区块
- 向**内核2品味模型**提供"角色声音"维度的偏好参照

VoiceProfile 的价值在于:不是"写了什么性格",而是"写了哪些**可检测**的声音规则"——让 AI 有客观对照基准,而非靠模糊描述猜。

```jsonc
// Character.voice_profile —— 完整结构(九节)
{
  // ─── 一、总体风格摘要(WritingAgent prompt 直接引用) ───
  "style_summary":
    "说话简短、克制、不废话。习惯用反问代替直接回答。
     在紧张或愤怒时更简短,极少超过两句。
     私下对信任之人偶尔会说长句,但仍保持克制语气。
     绝不主动解释自己的动机。",

  // ─── 二、口头禅与标志性短语 ───
  "catchphrases": [
    {
      "phrase": "随你。",
      "context": "不想表态或不在意时的万能回复",
      "frequency": "high"          // high / medium / low / rare
    },
    {
      "phrase": "你确定?",
      "context": "质疑对方判断时,不直接否定,用反问",
      "frequency": "medium"
    },
    {
      "phrase": "别废话了。",
      "context": "对方说了大段废话时",
      "frequency": "medium"
    },
    {
      "phrase": "我知道了。",
      "context": "接收信息时,不回应情绪内容,只确认信息",
      "frequency": "high"
    }
  ],

  // ─── 三、句式偏好 ───
  "sentence_patterns": {
    "preferred": [
      "短句(5–15 字为主)",
      "反问句代替否定(「你确定?」而非「不对」)",
      "省略主语(「走了。」而非「我走了。」)",
      "并列省略(「快,左边。」)",
      "停顿省略号表情绪(「……随你。」)"
    ],
    "avoided": [
      "长句连缀(超过 30 字的单句)",
      "主动解释动机(「我这样做是因为……」)",
      "感叹号(极少;仅极度愤怒时偶现)",
      "敬语/谦辞(「请」「不才」等)",
      "书面文绉绉措辞"
    ],
    "sentence_length_avg_chars": "8–18",
    "max_consecutive_long_sentences": 2    // 连续长句上限;超出则为 OOC 信号
  },

  // ─── 四、用词特征 ───
  "vocabulary_profile": {
    "register": "口语化武侠风,偏古朴但不晦涩",
    "positive_keywords": ["走", "看", "知道", "行", "无妨", "随你", "小心"],
    "negative_keywords": ["感动", "开心", "喜欢", "谢谢你", "我爱你", "真的吗太好了"],
    "domain_specific": {
      "combat":  "用简洁动词(「斩」「挡」「退」),不用华丽意象描写自身动作",
      "emotion": "绝不直接说「我很难过」;通过动作和短句间接传递(「走开。」「别靠近我。」)"
    }
  },

  // ─── 五、语气与情绪表达规则 ───
  "tone_rules": [
    {
      "situation": "陌生人/敌人对话",
      "tone": "冷漠、警惕;句子极短;常无回应直接离开",
      "example_line": "（沉默片刻）你说完了?"
    },
    {
      "situation": "信任伙伴对话",
      "tone": "仍克制,但偶尔出现 15–25 字的解释性语句;不主动分享情绪,但会回应对方情绪",
      "example_line": "你受伤了,先别动。……我没说你蠢,只是说你太急了。"
    },
    {
      "situation": "高压/战斗中",
      "tone": "指令式,字数最少;无废话",
      "example_line": "「左!」「退三步。」「现在。」"
    },
    {
      "situation": "被触碰创伤/旧事",
      "tone": "突然更沉默或截断对话;极少数情况下一句话字数反增(情绪决口)",
      "example_line": "够了。（转身）……她不是你该提的名字。"
    }
  ],

  // ─── 六、叙事视角下的内心独白风格(第三人称限制视角) ───
  "internal_monologue_style":
    "碎片化短句,不带完整语法。
     情绪不直接命名,只描述感受(「胸口发紧」「脑子空了片刻」)。
     偶尔出现自我质问(「为什么」反复出现但不得到答案)。",

  // ─── 七、OOC 检测信号(门槛1 直接使用的规则列表) ───
  // 设计要点:每条信号必须是"可用规则或统计方法客观检测的",不能写模糊描述
  "ooc_signals": [
    {
      "signal_id": "vpc_s01",
      "description": "连续超过 3 句长句(每句 > 25 字)",
      "detection_method": "rule",      // rule / llm / hybrid
      "severity": "high"
    },
    {
      "signal_id": "vpc_s02",
      "description": "直接说出情感词(「我很高兴」「我爱你」「感谢」)",
      "detection_method": "rule",
      "severity": "high"
    },
    {
      "signal_id": "vpc_s03",
      "description": "主动解释自身动机超过 30 字",
      "detection_method": "hybrid",
      "severity": "medium"
    },
    {
      "signal_id": "vpc_s04",
      "description": "使用感叹号超过 2 次且非战斗场景",
      "detection_method": "rule",
      "severity": "medium"
    },
    {
      "signal_id": "vpc_s05",
      "description": "对陌生人使用「谢谢」「请」等礼貌词超过 1 次",
      "detection_method": "rule",
      "severity": "low"
    }
  ],
  // 注:severity=low 的信号默认静默;只有 medium 以上才在门槛1侧栏展示
  // 规则信号先做快速检测;发现 signal_id + detection_method=hybrid 的才触发 LLM 二次确认

  // ─── 八、参考例句库(正例/反例) ───
  "reference_lines": {
    "positive_examples": [
      "我不在乎你的理由。结果才算数。",
      "（停顿）……你没事就好。",
      "别跟着我。",
      "路上小心。"
    ],
    "negative_examples": [
      "哦天啊,这真是太令我感动了,你的话让我重新找到了人生的意义!",
      "请允许我解释一下为什么我会做出这个决定,其实我的内心深处一直渴望……",
      "谢谢你告诉我这件事,我非常感激你的帮助!"
    ]
    // negative_examples 也作为 TasteModel.negative_list 的"角色声音"维度素材
  },

  // ─── 九、元数据 ───
  "version": 3,
  "built_by": "human",             // human / ai / hybrid
  "last_updated_chapter": "ch_050",
  "reviewer_notes":
    "第 40 章以后情感略有松动,可适当放宽 vpc_s02 在私下对话中的严格度"
}
```

**VoiceProfile 生命周期**:

```
人工录入初稿(或 AI 辅助生成 → 人工审核)
      │
      ▼
实现2 WritingAgent:prompt 引用 style_summary + catchphrases + tone_rules
      │
      ▼ 生成后
门槛1 OOC 检测器:规则扫描 ooc_signals(rule 类)
      │ 发现疑似
      ▼
LLM 二次确认(hybrid/llm 类信号)
      │ 确认为 OOC
      ▼
产出 RawConflictHint(PERSONALITY_OOC) → 门槛1聚合 → ConsistencyFlag
      │
      ▼
人工裁决:若为误报 → 软化对应信号阈值,更新 reviewer_notes
若角色弧光导致声音变化 → 创建新版本 VoiceProfile,绑定起效章节
```

**VoiceProfile 与 CharState 的关联**:当 `CharState.state_desc.affects_voice_profile = true` 时,系统提示作者"该角色在此章发生了弧光变化,是否更新 VoiceProfile?"——这是声音演变管理的关键钩子。

#### 3.1.3 CharState · 人物弧光时间线

**00 §4.3 基线定义**:

**CharState 写入时机**:

| 触发场景 | 写入方式 | `recorded_by` | `confidence` |
|---|---|---|---|
| 作者手动标注章节中的人物变化 | 前端表单 → API | `human` | `confirmed` |
| ReviewAgent 生成后自动推断 | 提取 pipeline → API | `ai` | `inferred` |

### 3.2 素材库(原料)→ 设定圣经 提炼流程

设定圣经与原料-素材库的关系:**素材 = 未提炼的原料;设定圣经 = 已确立的事实**。二者是两个不同层次的存在:

```
原料层 Material
  ├─ type: worldbuilding  (世界观碎片想法)
  ├─ type: research       (外部资料参考)
  ├─ type: inspiration    (随手记录的灵感)
  └─ status: raw / refined / archived
         │
         │  提炼流程(人工判断或 AI 辅助建议)
         ▼
门槛2 设定圣经
  ├─ SettingItem(rule/place/faction/term/item)
  ├─ Character + VoiceProfile
  └─ EntityRelation
```

**提炼流程步骤**:

```
1. 作者在原料库中标注 Material 为"可提炼"
2. AI 辅助将 Material.content 解析为目标实体的草稿 JSONB
   (调用 RefineAgent;见 §3.6 Prompt 模板)
3. 系统在设定圣经创建"待确认草稿条目"
4. 作者审核草稿:确认 / 修改 / 拒绝
5. 确认后:
   a. 设定条目 status = confirmed,触发 embedding 计算
   b. MaterialRef 记录关联(material_id → setting_item_id)
   c. 原料 Material.status 更新为 refined
```

**MaterialRef 记录**:用 00 §4.4 中的 `MaterialRef` 表记录素材到设定的溯源关系。`ref_type = "refined_into"`,便于日后追溯"这条设定源自哪个原始素材"。

**边界**:原料库负责原料的收集与标注;设定圣经负责确立和维护事实。提炼的判断权在人(作者),AI 只做草稿辅助。

### 3.3 自动注入流程:resolveEntities

#### 3.3.1 契约定义

```python
def resolveEntities(
    text: str,                            # 待分析文本(章节大纲/草稿片段)
    work_id: UUID,
    chapter_id: UUID,
    hint_entity_ids: list[UUID] = None,   # 规划 Agent 的提示实体(可选)
    max_candidates: int = 40,             # 最多返回候选数量
) -> list[SettingItemRef]:
    """
    解析 text 中出现的实体引用,返回相关 SettingItem 的候选引用列表。

    返回值不含实体完整 content,只含:
      id / type / name / embedding / relevance_score / match_reason / char_state_at_chapter

    调用方(实现4 assembleContext)接收此列表后,
    按相关性排序、按 token 预算裁剪,再加载完整 content 填入上下文。

    本函数只管"找到哪些实体与 text 相关",不管"按什么顺序填入 prompt"。
    """
```

```python
@dataclass
class SettingItemRef:
    id: UUID
    type: str                       # rule / item / place / faction / term / character
    name: str
    relevance_score: float          # 0.0–1.0
    match_reason: MatchReason       # EXACT_NAME / ALIAS / HINT / EMBEDDING
    embedding: list[float]          # 供实现4进一步排序
    char_state_at_chapter: dict     # 仅 type=character 时填充:该章时刻状态快照
    possibly_new_setting: bool      # True = 文本中出现但设定库无基准(提示补录)

class MatchReason(str, Enum):
    EXACT_NAME = "exact_name"       # 精确名称匹配,score=1.0
    ALIAS      = "alias"            # 别名/变体匹配,score=0.9
    HINT       = "hint"             # 规划层提示,score=0.95
    EMBEDDING  = "embedding"        # 向量语义召回,score=cosine similarity
```

#### 3.3.2 实现流程(五步伪代码)

```python
def resolveEntities(text, work_id, chapter_id,
                    hint_entity_ids=None, max_candidates=40):

    candidates: dict[UUID, SettingItemRef] = {}

    # ── 步骤 1:精确名称匹配(score=1.0) ──
    # EntityNameIndex(内存 Trie + AC 自动机)对全文做多模式扫描
    exact_matches = entity_name_index[work_id].lookup(text)
    for match in exact_matches:
        candidates[match.id] = SettingItemRef(
            id=match.id, type=match.type, name=match.name,
            relevance_score=1.0, match_reason=MatchReason.EXACT_NAME,
            embedding=match.embedding,
            char_state_at_chapter=_state_if_char(match, chapter_id),
            possibly_new_setting=False
        )

    # ── 步骤 2:别名匹配(score=0.9) ──
    # 检查 SettingItem.content['aliases'] 和 Character.traits 中的 distinguishing_marks
    alias_matches = alias_lookup(text, work_id)
    for match in alias_matches:
        if match.id not in candidates:
            candidates[match.id] = SettingItemRef(
                ..., relevance_score=0.9, match_reason=MatchReason.ALIAS, ...
            )

    # ── 步骤 3:hint_entity_ids 直接加入(score=0.95) ──
    # 实现1规划 Agent 在规划章节时已知会出现哪些核心实体
    if hint_entity_ids:
        for eid in hint_entity_ids:
            if eid not in candidates:
                item = db.get_entity(eid)
                if item:
                    candidates[eid] = SettingItemRef(
                        ..., relevance_score=0.95, match_reason=MatchReason.HINT, ...
                    )

    # ── 步骤 4:向量语义检索(仅当精确+别名结果 < 15 时触发) ──
    # 避免过度检索;对短大纲文本效果有限
    if len(candidates) < 15:
        query_embedding = embedding_model.encode(text[:512])
        semantic_hits = pgvector_search(
            query=query_embedding,
            work_id=work_id,
            top_k=max_candidates - len(candidates),
            min_score=0.65
        )
        for hit in semantic_hits:
            if hit.id not in candidates:
                candidates[hit.id] = SettingItemRef(
                    ..., relevance_score=hit.score,
                    match_reason=MatchReason.EMBEDDING, ...
                )

    # ── 步骤 5:补充 CharState 快照 + 过滤软删除 + 截断返回 ──
    valid_candidates = {}
    for k, ref in candidates.items():
        if db.is_deleted(k):
            continue
        if ref.type == "character" and ref.char_state_at_chapter is None:
            ref.char_state_at_chapter = get_char_state_at_chapter(k, chapter_id)
        valid_candidates[k] = ref

    sorted_refs = sorted(valid_candidates.values(), key=lambda x: -x.relevance_score)
    return sorted_refs[:max_candidates]
```

#### 3.3.3 与实现4的协作边界

```
本模块 resolveEntities(text)
      │
      │  返回 SettingItemRef[](候选+embedding,不含完整 content)
      ▼
实现4 assembleContext(chapter_id, draft_outline)
      │  ① 接收 SettingItemRef[] 作为"候选设定实体"
      │  ② 按 relevance_score + token 预算做最终裁剪
      │  ③ 加载入选实体的完整 content
      │  ④ 与历史摘要/伏笔/时间线事件拼装为 ContextBundle
      ▼
ContextBundle → 实现2 WritingAgent prompt
```

**关键边界**:

- `resolveEntities` **不做 token 计算**——只做实体语义解析与候选召回
- `assembleContext` **不做实体语义解析**——只做按预算排序与裁剪
- 两者通过 `SettingItemRef[]`(含 embedding 向量)交接,接口语义清晰

#### 3.4.2 validate 执行流程(五阶段)

```python
def validate(chapter_id, scope=ValidationScope.FULL):

    hints: list[RawConflictHint] = []
    chapter = db.get_chapter(chapter_id)
    segments = db.get_segments(chapter_id)
    full_text = " ".join(s.text for s in segments)

    # ── 阶段 A:从正文抽取"实体声明"(需 LLM,scope=FULL 才执行) ──
    # ExtractAgent 输入:正文 + 提示词(见 §3.6)
    # 输出:EntityMention[] = {entity_name, claim_type, claim_value, segment_id}
    if scope == ValidationScope.FULL:
        entity_mentions = extract_agent.extract_mentions(
            text=full_text, work_id=chapter.work_id
        )
    else:
        entity_mentions = []  # QUICK 模式跳过

    # ── 阶段 B:对每条声明,对照设定基准检查 ──
    for mention in entity_mentions:
        entity = db.resolve_entity_by_name(mention.entity_name, chapter.work_id)
        if entity is None:
            # 未知实体:产出"可能是新设定"提示,不产出冲突
            hints.append(RawConflictHint(
                hint_type=ConflictHintType.NAMING_INCONSISTENCY,
                severity="low",
                possibly_new_setting=True,
                description=f"「{mention.entity_name}」未在设定圣经中登记,建议补录",
                ...
            ))
            continue

        baseline = get_entity_baseline_at_chapter(entity.id, chapter_id)

        match mention.claim_type:
            case "ability":
                if not ability_matches(mention, baseline):
                    hints.append(RawConflictHint(
                        hint_type=ConflictHintType.ABILITY_INCONSISTENCY,
                        severity=assess_severity(mention, baseline),
                        ...
                    ))

            case "item_state":
                # SCORE 符号状态追踪(arXiv 2503.23512)【已核实】
                expected = baseline.get("symbolic_state")
                if expected in ("lost", "destroyed") and mention.claim_value == "active":
                    hints.append(RawConflictHint(
                        hint_type=ConflictHintType.ITEM_STATE_INCONSISTENCY,
                        severity="high",
                        description=f"物品「{entity.name}」设定状态为「{expected}」,但正文中出现其被使用",
                        evidence_from_bible=f"在第 {baseline['last_state_chapter']} 章已标记为 {expected}",
                        ...
                    ))

            case "relation":
                expected_relation = get_entity_relation_at_chapter(
                    entity.id, mention.target_entity_id, chapter_id
                )
                if expected_relation and not relation_compatible(mention, expected_relation):
                    hints.append(RawConflictHint(
                        hint_type=ConflictHintType.RELATION_INCONSISTENCY,
                        severity="medium", ...
                    ))

            case "rule_application":
                violated = check_rule_violations(mention, chapter.work_id)
                hints.extend(violated)

            case "appearance":
                if not appearance_matches(mention, baseline):
                    hints.append(RawConflictHint(
                        hint_type=ConflictHintType.ATTRIBUTE_INCONSISTENCY,
                        severity="low", ...
                    ))

    # ── 阶段 C:命名一致性检查(无需 LLM,全文扫描) ──
    # 检查同一角色/地点是否使用了不一致的称谓
    hints.extend(check_naming_consistency(full_text, chapter.work_id))

    # ── 阶段 D:VoiceProfile OOC 检查 ──
    # 对正文中的对话段落,逐角色对照 ooc_signals 做规则检测
    # detection_method=rule 的信号:正则/统计,无需 LLM
    # detection_method=hybrid 的信号:规则检测到疑似 → LLM 二次确认
    ooc_hints = check_ooc_by_voice_profile(segments, chapter.work_id)
    hints.extend(ooc_hints)

    # ── 阶段 E:返回原始 hint(不去重,由门槛1统一处理) ──
    return hints
```

### 3.8 百万字下的性能与规模

#### 3.8.1 设定规模预估

| 实体类型 | 百万字估算量 | PostgreSQL 单表承载评估 |
|---|---|---|
| Character | 50–300 个 | 轻松 |
| SettingItem | 200–800 条 | 轻松 |
| EntityRelation(含历史版本) | 100–600 条 | 轻松 |
| CharState | 300–2000 条 | 轻松 |
| VoiceProfile(嵌套在 Character) | 无独立表 | — |
| SettingItemRevision | 500–3000 条 | 轻松 |

> 【设计决策】全部实体合计在 PostgreSQL 单表属小数据量,百万字内完全无需分库、无需图数据库。pgvector IVFFlat 足够覆盖向量检索需求(00 §3 ponytail 原则)。

#### 3.8.2 向量检索性能

```sql
-- SettingItem 向量检索(pgvector IVFFlat)
CREATE INDEX idx_setting_item_embedding
    ON setting_items USING ivfflat (embedding vector_cosine_ops)
    WITH (lists = 100);    -- 设定量 < 1000 条,lists=50–100 足够

-- Character 向量检索
CREATE INDEX idx_character_embedding
    ON characters USING ivfflat (embedding vector_cosine_ops)
    WITH (lists = 50);
```

**延迟估算**:设定库 < 1000 条 + IVFFlat → 单次检索 < 5ms,远低于 LLM 调用延迟,不是性能瓶颈。

## §6 · 失败模式与缓解

### 6.1 注入过载:相关实体太多

**场景**:一章涉及 20+ 实体,全量注入超出 token 预算。
**缓解**:
- `resolveEntities` 只返回候选 id,不返回完整 content;token 预算控制在实现4
- 按 relevance_score 降序截断;优先保留主角 + 本章高频实体
- SettingItem(type=rule)提前判断本章是否真正触发该规则,否则降低 score

### 6.2 命名歧义:同名实体/多称谓

**场景**:"剑圣"可能是称号,也可能是专有名词。
**缓解**:
- EntityNameIndex 支持 `context_type` 过滤:武功场景中"剑圣"优先匹配 Character
- 歧义实体创建时强制填写 `aliases` 和 `disambiguation_note`
- 精确匹配发现歧义时,产出低优先级告警(不阻断写作)

### 6.3 设定未及时更新导致误报

**场景**:作者在正文写了角色的新能力,但未更新设定圣经 → validate 产出"能力矛盾"误报。
**缓解**:
- `RawConflictHint.possibly_new_setting = true` 时,门槛1前端展示为"可能是新设定?建议补录"而非"冲突"
- 作者确认后,触发"从正文自动创建/更新设定项"(ExtractAgent 辅助)
- MVP 阶段只提示不自动创建;增强版阶段再开启自动提炼

### 6.4 VoiceProfile 误报疲劳

**场景**:ooc_signals 过紧,正常对话频繁标红。
**缓解**:
- severity=low 的信号默认静默
- 采用"规则快速检测 → LLM 二次确认"双重模式:规则发现疑似 → LLM 才产出 hint
- 作者每次"误报"裁决后,软化对应信号阈值 + 更新 reviewer_notes

### 6.5 修订回流校验风暴

**场景**:修改核心设定触发 200+ 章重校验。
**缓解**:
- 工程4影响分析先算最小影响集(embedding 相关性 > 阈值的章节)
- 批次执行:每批最多 20 章,非活跃时段调度
- 非核心修改(名称拼写/外貌细节)只标黄,不触发完整 validate
- 提供"手动触发校验"按钮,作者掌控时机

### 6.6 设定圣经自身内容冲突

**场景**:A 是 B 的师父且 B 是 A 的师父。
**缓解**:
- EntityRelation 录入时**同步**做对称/传递约束检查:

```python
# 若 A→B relation="师父",检查是否已存在 B→A relation="师父"
# 若存在则拒绝,要求作者确认或修正
def check_relation_symmetry_violation(
    src_entity_id: UUID,
    dst_entity_id: UUID,
    relation: str,
    work_id: UUID
) -> list[str]:
    """返回违规描述列表;空列表表示无冲突"""
    ...
```

- SettingItem(type=rule)录入时,AI 异步检查是否与已有规则逻辑矛盾(低优先级)
- 定期运行"设定圣经自检"作业(工程7路线图)

### 6.7 CharState 推断精度不足

**场景**:ReviewAgent 自动推断的 CharState 条目人工确认率低(< 60%),增加而非降低人工负担。
**缓解**:
- 所有 AI 推断条目默认 `confidence=inferred`,在 UI 以灰色/虚线展示,不影响主流程
- MVP 阶段关闭自动推断,只开启手动录入;增强版再开启推断+确认流程
- 工程6度量追踪"推断确认率",低于阈值时关闭自动推断功能开关

## §7 · MVP vs 完整版

### 7.1 MVP 阶段

**目标**:跑通"设定写入 → 生成时注入 → 基础校验"核心闭环。

| 功能 | MVP 实现 | 完整版目标 |
|---|---|---|
| Character CRUD | traits / motivation / voice_profile 手动录入 | + AI 辅助生成 VoiceProfile 初稿 |
| SettingItem CRUD | rule/item/place/faction/term 五类,手动录入 | + 设定演变版本链 |
| EntityRelation | 基础录入,无 valid_to 追踪 | + 完整演变历史 + 受控词表校验 |
| CharState | 手动录入,无 AI 自动推断 | + ReviewAgent 推断 + 确认流程 |
| VoiceProfile | 手动录入结构化 JSON | + AI 辅助生成 + OOC 规则检测 |
| resolveEntities | 精确名称匹配 + Hint(无向量检索) | + 向量语义检索 + 别名匹配 |
| validate | scope=QUICK:物品符号状态 + 命名一致性 | + scope=FULL:能力/关系/规则/OOC 全量 |
| 修订回流 | 修改设定后手动触发重校验 | + 自动影响分析 + 批次调度 |
| 设定版本化 | 无版本历史 | + SettingItemRevision 完整版本链 |
| 素材提炼 | 无 | + RefineAgent 辅助提炼 |

**MVP 优先验证的核心假设**:

1. 精确名称匹配 + Hint 注入能覆盖 80%+ 的"生成时需要的设定"吗?
2. 物品符号状态校验(scope=QUICK)的误报率是否可接受?
3. VoiceProfile 手动录入的成本,作者能持续接受吗?

### 7.2 增强版阶段

- 向量语义检索(pgvector + IVFFlat)
- AI 辅助 VoiceProfile 生成
- CharState 自动推断(ReviewAgent + 人工确认)
- validate scope=FULL:能力/关系/规则/OOC 全量检查
- SettingItemRevision 版本历史
- 基础修订回流(自动影响分析 + 触发受影响章节重标记)
- 素材→设定提炼流程(RefineAgent)

### 7.3 完整版阶段

- EntityRelation 完整演变追踪(valid_from/to 双版本)
- 设定演变全链路可视化(人物弧光时间轴 UI,工程2)
- 自动影响分析 + 批次调度重校验(工程4深度集成)
- 设定圣经自检定期作业
- 多 POV 线路的设定可见性控制
- 设定条目依赖关系图("霜华剑的效果依赖寒铁材质规则")
- VoiceProfile 阶段性演变版本(绑定起效章节)

## §9 · 开放问题

### 9.1 待实验验证

**Q1 · VoiceProfile ooc_signals 规则精确率**
手工设计的规则(连续长句/直接情感词)在实际写作中误报率是多少?需用 10–20 章样本测试各信号的 false positive 率,再决定是否开启、阈值如何设置。若 FP > 20%,应降级该信号为 low 或关闭。

**Q2 · resolveEntities 名称匹配覆盖率**
在真实章节大纲文本中,精确名称匹配能覆盖多少应该被注入的实体?MVP 阶段需测量"漏注入率"——若超过 20%,则需提前开启别名匹配或向量检索。

**Q3 · validate 最优 scope 粒度**
对每章都做 scope=FULL(含 LLM ExtractAgent 调用)的成本,在百万字尺度下是否可接受?是否需要"无 LLM 快速检查 + 有 LLM 精检"两档模式?建议设计实验:对比 FULL vs QUICK 的冲突发现率与成本。

**Q4 · CharState 自动推断精度**
ReviewAgent 自动推断的 CharState 人工确认率大约是多少?若低于 60%,自动推断会增加负担而非降低——MVP 阶段应关闭该功能开关。

**Q5 · 修订回流最小影响集准确度**
工程4影响分析的"最小受影响章节集"与人工判断的"真正需要重校验章节集"的覆盖率/误报率如何?需设计对照实验验证。

### 9.2 待澄清设计决策

**Q6 · VoiceProfile 阶段性演变方案**
角色在第 40 章后声音发生变化时:方案 A = 在同一 JSONB 中追加 `arc_variants[]`;方案 B = 创建新版本 VoiceProfile 绑定起效章节(利用 SettingItemRevision)。
目前倾向方案 B(与版本化机制统一),待实现2、门槛1对齐后确认。

**Q7 · 多 POV 设定可见性**
多视角叙事中,某些设定是"读者知道但特定角色不知道"的信息。validate 校验时是否引入"角色视角过滤"?目前 v1 统一按"作者全知视角"校验;多 POV 支持推迟至完整版。

**Q8 · faction 内部层级结构**
复杂势力(有多个派系的大组织)的树形子结构:嵌套 JSONB 还是多条 SettingItem + EntityRelation 链接?待工程2前端交互设计确认。

**Q9 · ExtractAgent 从正文自动创建设定项的边界**
自动创建的精度阈值是多少?过低产生大量噪声条目。建议 MVP 只提示不自动创建;完整版再开启,阈值由工程6度量调整。

**Q10 · VoiceProfile 与 TasteModel 的关系**
VoiceProfile 的 `negative_examples` 是否同步回流给内核2 `TasteModel.negative_list`(角色声音维度的"AI腔黑名单")?若是,需设计同步机制。这是门槛2与内核2的跨层联动,待内核2文档明确后对齐。

> **与兄弟模块的对齐备忘(供实现2/4、门槛1、工程4、原料库作者参考)**
>
> - **实现4 · 记忆与检索**:`resolveEntities` 返回 `SettingItemRef[](含 embedding + relevance_score)`,由 `assembleContext` 做最终 token 感知裁剪和上下文拼装。双方边界:本模块管"实体语义解析与候选召回",实现4管"按预算排序与上下文拼装"。两者通过 SettingItemRef 接口交接,不越界。
>
> - **门槛1 · 连贯性保障**:调用 `validate(chapterId)` 获取 `RawConflictHint[](设定侧视角)`;同时调用 `get_all_ooc_signals(work_id)` 获取所有角色的 OOC 检测规则。`ConsistencyFlag` 由门槛1创建,本模块只产出 hint 不写 flag,职责不越界。
>
> - **实现2 · 写作生成**:`WritingAgent` 在拼装 prompt 时,从 ContextBundle 中取 `Character.voice_profile.style_summary` + `tone_rules` + `catchphrases` 填入写作 prompt 的"角色声音约束"区块。具体 prompt 拼装格式在实现2文档定义;本模块只确保字段齐备。
>
> - **工程4 · 版本与回流**:设定变更后,本模块通过消息队列推送"设定变更事件";工程4执行影响分析,返回受影响章节列表,触发重校验。双方通过消息队列解耦,不直接调用。
>
> - **原料 · 素材库**:素材库负责原料收集与标注;本模块负责提炼确认的设定事实。提炼流程通过 `refine_material_to_setting` API 和 `MaterialRef` 记录完成跨模块溯源。
